# Указания Codex для переноса Мольберты.ру

## Задача

Воссоздать согласованную версию v129 на WordPress с WooCommerce, сохранив дизайн, URL, контент, цены, галереи, мобильное поведение и SEO. Реализация ведётся в отдельной папке wordpress-site; эталон не переписывается.

## Сначала

- Прочитать README.md, snapshot.json, docs/01-PLAN.md, 02-ARCHITECTURE.md, 03-DATA-MAP.md и 08-CODEX-TASKS.md.
- Выполнить tools/validate_package.py; определить реальный путь к эталону.
- Зафиксировать версии WordPress/WooCommerce/PHP и действующие инструкции в целевом репозитории. Новые требования пользователя имеют приоритет.
- Проверить текущее состояние staging, активную тему и плагины до любых изменений.

## Обязательные правила

1. Итоговый HTML и CSS v129 — визуальный эталон. Исторические заметки могут быть устаревшими.
2. Не переносить assets/app.js целиком: он заменяет шапку, футер, страницы и использует статический каталог. Общие элементы, цены и контент выводить PHP; клиентский JS отвечает за взаимодействия.
3. Не запускать полный build/prerender в reference. Для чтения достаточно serve.py.
4. Сохранить 91 sourceId/id товара, 34 корневых адреса категорий с их иерархией, 4 адреса статей. Переимпорт не создаёт дубликаты и не удаляет отсутствующие записи автоматически.
5. Для карточек: название в листинге — исходное name, H1 — поле h1 выгрузки. Для мольбертов H1 содержит Мольберт. Не добавлять кавычки в названия товаров.
6. Цены рассчитываются на сервере из сохранённых опций; tier, indices и quantity проверяются. Денежная сумма из браузера не принимается как достоверная.
7. Все 717 fixtures должны проходить в серверном ценовом движке. wholesaleOnly и минимальная партия обязательны. Строки корзины разных комплектаций не объединять.
8. Формы реально отправляют или регистрируют заявку только после подключения обработчика. Успешный ответ показывать после успешного результата; при сбое сохранять ввод и показывать ошибку.
9. Согласие обязательно и не предустановлено; ссылки privacy/consent работают. Поля ИНН и реквизиты в оптовой форме отсутствуют.
10. Не публиковать секреты, не помещать их в Git или пакет. Доступы запрашиваются у оператора только когда соответствующий этап действительно зависит от них.
11. Работать на staging. DNS, боевой SMTP, платёжные операции и замена production не выполняются только на основании подготовки этого пакета.
12. Перед выпуском предоставить оператору конкретный результат: diff, URL staging, выполненные проверки, резервную копию и план отката.
13. Сохранить внутренние признаки происхождения showcase/reviews и разделение клиентов и примеров пространств; не добавлять из них AggregateRating в Product.
14. Не переписывать оригинальный текст О компании и статей. Не возвращать внешние ссылки в текст статей.
15. Не вводить новые h2/h3 вместо согласованных div/span, не возвращать нумерацию блоков главной.

## Работа по этапам

Следовать docs/08-CODEX-TASKS.md последовательно. Для каждого этапа фиксировать изменённые файлы, команды проверок и фактический результат в progress.md. Незавершённые интеграции помечать явно. Не выдавать импорт черновиков за готовый перенос.

## Завершение

Создать тему, рабочий модуль бизнес-логики, инструкции редактору, карту редиректов и итоговый отчёт приёмки. Проверить серверный HTML без JS, мобильные меню/корзину/формы, галереи, все маршруты и метаданные. Данные из этого пакета не требуют повторного переписывания вручную.
